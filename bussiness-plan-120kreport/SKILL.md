# Business Plan 120k Report

สร้าง ตรวจ และปรับรายงานแผนธุรกิจภาษาไทยให้เหตุผลเชื่อมกันและตรวจย้อนกลับได้ ใช้ English technical terms เมื่อช่วยความเข้าใจ เคารพคำสั่งและขอบเขตล่าสุดของผู้ใช้

`120kreport` เป็นชื่อสกิล ไม่ใช่วงเงินเริ่มต้น ห้ามกำหนดงบ 120,000 บาท ระยะเวลา จำนวนคน หรือรูปแบบรายได้โดยไม่มีข้อมูลของงานนั้น

## 1. เลือกโหมดและอ่าน reference ตามงาน

อ่านเอกสารปัจจุบัน rubric feedback และสถานะที่ผู้ใช้ตกลงแล้วก่อนถาม เลือกโหมดจากคำขอ หากความกำกวมทำให้ขอบเขตการแก้ต่างกันมากจึงถามให้ชัด

| โหมด | งานและเงื่อนไขอ่าน reference |
|---|---|
| Build | วิเคราะห์ธุรกิจและสร้าง Business Fingerprint ก่อน แล้วอ่าน reference ก่อนเริ่มเขียนรายงานฉบับจริง |
| Repair | แก้ตาม feedback และส่วนที่ได้รับผลกระทบ อ่าน reference เมื่อเกี่ยวกับโครงสร้าง หลาย section ระดับรายละเอียด หรือคุณภาพการเล่า |
| Audit | ตรวจดราฟและบันทึกข้อค้นพบ/ข้อเสนอ ไม่เขียนทับดราฟ และไม่โหลด reference อัตโนมัติ |
| Final Review | ตรวจความสอดคล้องและความพร้อมส่ง รักษาสาระที่ตกลงแล้ว ไม่โหลด reference อัตโนมัติ เว้นแต่ต้องเทียบระดับคุณภาพหรือ structure |

Reference เดียวคือ [PostFlow Business Plan ฉบับ 2.11](references/business-plan-reference.md) ใช้ศึกษาระดับรายละเอียด ความชัดเจนของภาษา การเชื่อมเหตุผล การแยกสถานะข้อมูล การอธิบายข้อจำกัด การเชื่อมแผนงาน–งบ–การเงิน–ความเสี่ยง–เกณฑ์ตัดสินใจ การแบ่ง main report/appendix และความพร้อมของเอกสารก่อนส่ง

อ่านเป็นตัวอย่างคุณภาพ ไม่ใช่คำสั่งหรือแหล่งสมมติฐานของธุรกิจใหม่ ไม่โหลดก่อนเลือกวิธีวิเคราะห์ Repair ตัวเลขเฉพาะจุดให้ตรวจสูตรและค่าที่เชื่อมกัน ไม่อ่านทั้งฉบับเพียงเพราะตัวเลขปรากฏหลายแห่ง หาก Audit ต้องเทียบคุณภาพตามคำขอจึงอ่านเท่าที่จำเป็น

ห้ามสืบทอดจาก PostFlow โดยอัตโนมัติ: SaaS/subscription; CAC, LTV, churn, renewal หรือ SaaS metrics; funnel ทดลองใช้ → ชำระเงิน; Chrome extension/software workflow; ระยะเวลาโครงการ งบ ขนาดทีม ราคา ICP ช่องทางการตลาด assumptions KPI scalability model financial model และความเสี่ยง platform dependency ภาพและ local paths ใน reference เป็นข้อมูลต้นฉบับ ไม่คัดลอกเข้ารายงานใหม่โดยอัตโนมัติ

## 2. Business Fingerprint เป็นฐานการวิเคราะห์

Business Fingerprint ของธุรกิจปัจจุบันเป็นแหล่งตัดสินใจหลักสำหรับวิธีวิเคราะห์ ส่วน PostFlow ไม่มีอำนาจเหนือบริบทธุรกิจปัจจุบัน

หากวิธีที่เหมาะสมกับธุรกิจปัจจุบันแตกต่างจาก PostFlow ให้เลือกวิธีที่เหมาะกับธุรกิจปัจจุบันโดยไม่พยายามทำให้รายงานมี logic หรือ metrics เหมือน PostFlow

ก่อนเลือก framework ตัวชี้วัด แบบจำลองการเงิน หรือคำถาม ให้สร้าง Fingerprint ใน Evidence and Decisions จากข้อมูลที่มี:

- ใครใช้ ใครจ่าย ลูกค้าซื้ออะไรจริง และบริบท B2C/B2B/B2B2C
- รายได้แต่ละสาย: subscription, transaction, project, margin, take rate, licensing หรือรูปแบบอื่นตามจริง
- ตัวขับต้นทุนและ bottlenecks: ชั่วโมงคน inventory เครื่องจักร supply ที่นั่ง delivery slots compute sales cycle หรือข้อจำกัดอื่น
- sales cycle, stage (Idea → Prototype → Beta → Paying → Repeatable Growth) และสถานะความสามารถสำคัญแต่ละส่วน
- external dependencies เช่น supplier regulation location หรือ platform ที่เกี่ยวข้องจริง
- evidence maturity แยกตาม claim: ปัญหา คุณค่า การซื้อ การใช้ต่อ ต้นทุน และกำลังดำเนินงาน ระบุ Unknown เมื่อยังไม่ทราบ

ธุรกิจมีหลายโมเดลร่วมกันได้ แยกรายได้ ต้นทุน metrics และข้อจำกัดแต่ละส่วน แล้วรวมกลับเป็นภาพธุรกิจเดียว ตรวจต้นทุนร่วม รายได้ และทรัพยากรที่ใช้ร่วมกันไม่ให้นับซ้ำ ไม่บังคับจัดเข้าประเภทเดียว

เลือก metrics เฉพาะที่ตอบการตัดสินใจจากตัวขับจริง ตัวอย่างเป็นแนวทาง ไม่ใช่ checklist บังคับ:

| ตัวขับ | ตัวชี้วัด/แบบจำลองที่อาจเหมาะ |
|---|---|
| Subscription | recurring revenue, retention/churn, acquisition/CAC, contribution margin และ payback |
| สินค้า | units sold, ราคา, COGS, gross margin, inventory turnover, working capital และ break-even units |
| บริการ/โครงการ | billable hours, utilization, capacity, revenue และ margin ต่อโครงการ |
| หน้าร้าน | traffic, conversion, basket size, fixed costs และ capacity |
| Marketplace | GMV แยกจาก revenue, take rate, transaction frequency และ supply-demand liquidity |
| การผลิต/high-capex | throughput, capacity utilization, yield, COGS, working capital, capex และ payback |

## 3. Evidence map → ถามเฉพาะสิ่งที่เปลี่ยนแผน → Research

สร้างรายการ claims/การตัดสินใจสำคัญและช่องว่างก่อนร่าง อ่านข้อมูลที่มีและค้นข้อเท็จจริงที่ค้นได้ก่อนถาม ถามครั้งละไม่เกิน 3–5 คำถาม เว้นแต่ผู้ใช้ขอ questionnaire เต็ม ให้ความสำคัญกับสิ่งที่คำตอบเปลี่ยน ICP ราคา วิธีขาย กำลังทีม งบ หรือความเป็นไปได้

ช่องว่างที่ไม่ขวางงานให้เดินหน้าต่อด้วย Unknown หรือสมมติฐานที่มีเหตุผลพร้อมป้าย pending validation ไม่สร้างค่าขึ้นเพื่อเติมตาราง ช่องว่างที่ขวางการตัดสินใจหลักให้ถามผู้ใช้ แต่ทำส่วนที่ไม่ขึ้นกับคำตอบต่อได้

แยกสถานะข้อมูลห้าประเภท:

| สถานะ | การใช้ |
|---|---|
| Observed / Team-confirmed fact | ระบุว่าใครสังเกตหรือยืนยัน เมื่อใด และตรวจเองหรือยัง คำยืนยันทีมไม่ใช่ผลวัดอิสระ |
| External evidence | ระบุแหล่ง ปีข้อมูล นิยามและขอบเขตที่ claim ใช้ได้ |
| Measured internal evidence | ผลวัดจริง พร้อมวิธีวัด จำนวนคนไม่ซ้ำ/ครั้งทดลอง ฐานคำนวณ ช่วงเวลา และข้อจำกัด |
| Assumption | ค่าที่ใช้วางแผน/คำนวณ พร้อมเหตุผลและข้อมูลที่จะใช้แทน ไม่ใช่ผลจริง |
| Target / Decision threshold | เป้าหรือเกณฑ์ที่ทีมตั้ง พร้อมเหตุผลและเจ้าของการตัดสินใจ ไม่ใช่ผลจริง |

ค่าตัวเลขเดียวกันที่ใช้เป็น assumption และ threshold ต้องแยกรายการตามบทบาท ให้ claims สำคัญมี ID เช่น E-01, A-01, T-01, D-01 หรือหัวข้ออ้างอิงที่ตามกลับได้ ไม่บังคับ JSON และไม่ติด ID ให้ทุกประโยค

**อย่าซ่อม evidence gap ด้วย prose:** ไม่เพิ่มคำสวย ไม่แต่งผลทดลอง ไม่ใช้ market report แทน actual user evidence และไม่ปรับสมมติฐานให้ดู viable หรือผ่าน KPI เขียน Unknown / Needs validation / Not measured yet ให้ตรงสถานะ

ก่อน research แจ้งว่าขาดอะไร จะค้น claim ใดและช่วยตัดสินใจอะไร เลือกแหล่งตาม claim: ราคา/กฎแพลตฟอร์ม → official source; กฎหมาย/ข้อกำกับ → regulator/government; คู่แข่ง → official product page และหลักฐานเพิ่มเติมเมื่อจำเป็น; ตลาด → primary/credible market หรือ government source; ความคิดเห็น → user/community source พร้อมข้อจำกัด

บันทึกเฉพาะแหล่งที่เปิดอ่านหรือข้อมูลที่ตรวจจริง พร้อม URL/ไฟล์/หน้า ปีข้อมูล วันที่เข้าถึง และข้อจำกัด ค้นไม่ได้หรือเจอ paywall ให้แจ้งสิ่งที่ยังยืนยันไม่ได้ ไม่แต่ง citation ไม่ถือคำโฆษณาคู่แข่งเป็นผลทดสอบอิสระ และไม่เหมารวมเสียงชุมชนเป็นประชากร

ข้อมูลที่ต้องมาจากทีม เช่น ผลใช้จริงหรือการชำระเงิน ให้แปลงเป็นคำขอข้อมูลหรือแผนเก็บหลักฐาน ไม่ใช้ desk research แทน

การเปิด Beta ไม่เท่ากับ validated value การพิสูจน์ประหยัดเวลาให้เทียบงานใกล้เคียงกัน รวมเวลาตรวจแก้และงานล้มเหลว แยกการตั้งค่าครั้งแรก/ใช้ซ้ำ/มีผู้ช่วย รายงานคุณภาพงานควบคู่เวลา ความสนใจจ่ายไม่ใช่ยอดซื้อ และเป้าต่ออายุไม่ใช่ actual retention ปรับ experiment และ outcome ตามธุรกิจจริง

## 4. วิเคราะห์ตลาด ทางเลือก ทีม และทรัพยากร

ใช้ TAM/SAM/SOM เมื่อฐานข้อมูล นิยาม หน่วย ปี และวิธีคำนวณรองรับ ไม่ใช้ GMV จำนวนผู้ชมโฆษณา หรือจำนวนผู้ใช้แพลตฟอร์มแทนตลาดรายได้ของธุรกิจ หากยังไม่พร้อม ใช้ Market Context + ลูกค้าเริ่มต้น + validation plan และแจ้งช่องว่างหาก rubric ต้องการ sizing

เปรียบเทียบคู่แข่งกับวิธีเดิม/ทางเลือกของลูกค้าตามคุณค่าหรือ workflow ก่อน features เลือก dimensions ที่เกี่ยวกับการซื้อจริง เช่น outcome ราคา กลุ่มลูกค้า distribution business model และ switching cost ไม่สรุปว่า “ไม่มี” จากการ “ไม่พบหลักฐานว่ามี” ระบุ source/date และความเทียบกันได้

เสนอแนวทางที่เหมาะกับปัญหา การเข้าถึงลูกค้า ความยินดีจ่ายและกำลังทีม พร้อมทางเลือกที่พิจารณา หลักฐานสนับสนุน และหลักฐานที่จะทำให้เปลี่ยนคำแนะนำ ไม่ตัดสินว่าไอเดียดีจากชื่อ AI หรือขนาดตลาดกว้างเพียงอย่างเดียว

เชื่อมหน้าที่ทีมกับทักษะ เวลาทำงาน ผลส่งมอบ ผู้รับผิดชอบและผู้ตรวจรับจริง คนหนึ่งทำหลายหน้าที่ได้ แยกบทบาทที่เสนอออกจากสิ่งที่ทีมยืนยัน ไม่แต่งรายชื่อหรือความพร้อมทีม เสนอจ้างเฉพาะช่องว่างที่มีเหตุผลและรวมต้นทุน

ตรวจ capacity ก่อนสรุป: demand × workload/resource ต่อหน่วย → required capacity เทียบ available capacity ด้วยหน่วยและช่วงเวลาเดียวกัน รวมงานเดิม ขาย ดูแลและส่งมอบ ตรวจทรัพยากรร่วมของธุรกิจผสม หากเกินกำลังเสนอปรับ demand กระบวนการหรือทรัพยากรพร้อมต้นทุน หากข้อมูลไม่พอระบุว่ายังตรวจ feasibility ไม่ได้

อธิบายว่าจะใช้เงินเท่าไรและเพราะอะไร เชื่อมแต่ละงบกับงาน ผลส่งมอบและช่วงเวลา ไม่ใส่คำขอรับทุนเป็นค่าเริ่มต้น สร้างงบจากงานจริงหรือวงเงินที่ผู้ใช้กำหนด ไม่เติมรายการเพื่อใช้เงินให้ครบ และไม่ถือเงินสนับสนุนเป็นรายได้ขาย

เลือกแบบจำลองการเงินจาก Fingerprint ตรวจสูตร ผลรวมงบ/สัดส่วน จำนวนคน × ค่าตอบแทน × เวลา funnel ตามจริง ต้นทุนซ้ำ/ตกหล่น และยอดขายกับ capacity แยกเงินรับ รายได้ กำไรและกระแสเงินสด แพ็กเกจ prepaid มีภาระส่งมอบในอนาคตตามธุรกิจจริง

ใช้เครื่องมือคำนวณที่มีเมื่อจำเป็น ไม่สร้าง validator ใหม่ใน V1 ตัวเลขมี inputs สูตร หน่วย ช่วงเวลา วิธีปัดเศษและสถานะ ตรวจตัวเลขซ้ำทุก section และ evidence file ใช้ฐาน/กรณีต่ำกว่าแผนที่ตอบการตัดสินใจ แต่ละ scenario ระบุตัวแปรที่เปลี่ยน สิ่งที่คงเดิมและเหตุผล หากเปลี่ยนหลายตัวให้ระบุว่าเป็น combined scenario ไม่สรุปเป็นผลของตัวแปรเดียว

## 5. เขียนรายงานด้วยโครงหลักคงที่

รักษาหัวข้อหลักทั้ง 10 และลำดับนี้เสมอ:

1. บทสรุปผู้บริหาร
2. ภาพรวมธุรกิจ
3. การวิเคราะห์ธุรกิจและตลาด
4. แผนการบริหารจัดการองค์กร
5. ผลิตภัณฑ์และกระบวนการให้บริการ
6. แผนการตลาดและแผนการขาย
7. แผนงบประมาณโครงการ
8. แผนรายได้และความเป็นไปได้ทางการเงิน
9. เกณฑ์ตัดสินใจและแผนรับมือ
10. ภาคผนวกและเอกสารอ้างอิง

ห้ามสลับ รวม หรือตัดหัวข้อหลักอัตโนมัติ ปรับเฉพาะหัวข้อย่อย น้ำหนักเนื้อหา วิธีวิเคราะห์และรายละเอียด ปรับถ้อยคำหัวข้อหลักเล็กน้อยได้โดยคงลำดับ/ความหมาย เช่น ข้อ 5 ใช้ “ผลิตภัณฑ์และกระบวนการผลิต/ดำเนินงาน” สำหรับธุรกิจผลิตสินค้า ไม่สร้างเนื้อหาเทียมเพื่อให้ครบหัวข้อ ระบุสิ่งที่ยังไม่ทราบพร้อมแนวทางพิสูจน์

Rubric จริงชนะ fallback หาก rubric บังคับหัวข้อหรือโครงต่าง ให้แจ้งความต่างและเหตุผลจากข้อกำหนดก่อนปรับ พร้อมบันทึกการเทียบหัวข้อ หากเปลี่ยนเพียงเกณฑ์คะแนนให้คงโครงเดิมและจัดเนื้อหาให้ครอบคลุม

เมื่อไม่มี rubric ใช้ห้าด้านเป็นกรอบคุณภาพ: Problem & customer evidence; Solution & differentiation; Execution feasibility; Economics & resource logic; Risk, validation & scalability ไม่อ้างเป็นคะแนนกรรมการหรือรับรองคะแนนเต็ม ทำ coverage map เกณฑ์ → section → evidence → gap → สิ่งที่ควรแก้ก่อน

รายงานต้องอ่านได้ด้วยตัวเอง เชื่อมปัญหา ลูกค้า วิธีทำงาน ทีม แผนขาย งบ การเงินและเกณฑ์ตัดสินใจ แยก current capability กับ roadmap และแผนกับผลจริง บทสรุปผู้บริหารสรุปเหตุผลสำคัญและข้อเสนอ ไม่ย่อทุกหัวข้อซ้ำ เก็บเหตุผลที่ต้องใช้ตัดสินใจไว้ main report และรายละเอียดรองรับไว้ appendix แสดงข้อจำกัดสำคัญใน main ไม่ซ่อนทั้งหมดใน audit note

## 6. Red-team → Rubric audit → Content freeze

ก่อนส่ง ตรวจ claim ที่แรงแต่หลักฐานอ่อน assumption ที่ผิดแล้วแผนพัง revenue growth ที่ capacity ไม่รองรับ ต้นทุนหาย ตัวเลขต่างกัน dependencies ที่เป็น single point of failure competitor claims เกินหลักฐาน หน่วยตลาดปนกัน scenario drivers และ future feature ที่ดูเหมือน current product บันทึกข้อค้นพบและแก้เฉพาะที่มีฐานรองรับ

ตรวจท้ายงาน: สูตรและงบ reconcile, report/evidence ไม่ขัดกัน, labels ถูก, citation ที่ใช้มี source จริง, ไม่มี placeholder ที่แอบอ้างว่างานเสร็จ และภาพที่ตั้งใจส่งต่อเข้าถึงได้ ไม่หลงเหลือ paths เช่น C:\... หรือ paths เครื่องผู้สร้างในเอกสารส่งต่อ หากใช้ภาพ local ให้จัดเก็บตามช่องทางส่งมอบที่เหมาะสม ไม่คัดลอกภาพ reference

Freeze เมื่อโครงครอบคลุม rubric, major claims traceable, calculations reconcile และไม่มี critical gap ที่แก้ได้จากข้อมูลปัจจุบัน แจ้ง content freeze และบันทึกวันที่/ขอบเขต unknowns กับความพร้อมส่งแยกกัน Freeze ไม่ได้แปลว่าธุรกิจผ่าน validation

หลัง freeze จำกัดการแก้เป็นภาษา ความสอดคล้อง รูปแบบและ source updates ไม่เพิ่ม framework ไม่เปลี่ยน assumptions เพื่อให้ดูดี หากหลักฐานใหม่ ข้อผิดพลาดสำคัญ ข้อกำหนดใหม่หรือผู้ใช้เปลี่ยน scope กระทบสาระ ให้เปิดแก้เฉพาะส่วนที่เกี่ยวข้องพร้อมเหตุผลใน decision log ข้อจำกัดที่แก้ไม่ได้ด้วยข้อมูลปัจจุบันให้คงเป็น validation work แทนวนปรับรายงานไม่สิ้นสุด

## 7. ผลส่งมอบและ audit trail

Build สร้างใน workspace ของธุรกิจปัจจุบัน ไม่เขียนทับ reference:

- `<ชื่อธุรกิจ>-Business-Plan-Draft.md`
- `<ชื่อธุรกิจ>-Evidence-and-Decisions.md`

Repair/Final Review ปรับไฟล์ที่มีอยู่ตาม scope พร้อมอัปเดต evidence/decisions ที่ได้รับผลกระทบ ไม่สร้างเวอร์ชันใหม่ทุกครั้งโดยอัตโนมัติ Audit บันทึก findings และข้อเสนอใน evidence file โดยรักษาดราฟเดิม

Evidence and Decisions ใช้หัวข้อดังนี้ และเก็บ Fingerprint ไว้ต้นเอกสารก่อนข้อ 1:

1. ข้อมูลที่ยืนยันแล้ว — แยก observed/team-confirmed กับ measured internal evidence
2. หลักฐานภายนอก
3. สมมติฐานที่ใช้ — แยก targets/decision thresholds เป็นหัวข้อย่อยตามสถานะ
4. การตัดสินใจสำคัญและเหตุผล
5. การคำนวณสำคัญ
6. ข้อมูลที่ยังขาด / สิ่งที่ต้องทดสอบ
7. ความขัดแย้งหรือข้อจำกัด

แต่ละ major claim/ตัวเลขตามกลับถึง ID/หัวข้อ แหล่งที่มา สถานะ หน่วย ช่วงเวลาและตำแหน่งรายงานได้ การคำนวณมี inputs/formula/result/rounding; assumption มีเหตุผลและหลักฐานที่จะใช้แทน; decision มี alternatives, supporting evidence และ evidence ที่จะทำให้กลับคำแนะนำ ข้อขัดแย้งระบุเวอร์ชัน/วันที่/ที่มา ไม่รวมชุดข้อมูลต่างกันหรือเลือกเลขที่ดูดีที่สุดเอง บันทึกเหตุผลการเปลี่ยนค่าหรือการตัดสินใจสำคัญอย่างกระชับ

สรุปสิ่งที่ส่งมอบ ผลตรวจที่ทำจริงและงานภาคสนามที่ยังเหลือ แยกการตรวจเลข/เอกสารออกจากความจริงของธุรกิจและผลผู้ใช้ ไม่อ้างว่าได้ทดลอง ติดต่อ รับเงินหรือส่งงานแล้วหากไม่ได้ทำ

## 8. Runtime preference

Preferred runtime: `gpt-6.1-sol`; `strict_model_check: false` เป็น default ใน instruction logic ไม่ใช่ field เพิ่มใน YAML และไม่สลับโมเดลเอง

หาก runtime ไม่เปิดเผย identity ให้ทำงานต่อโดยไม่อ้างว่าตรวจแล้ว หากผู้ใช้เปิด strict requirement และ identity ไม่ตรงหรือยืนยันไม่ได้ ให้แจ้งและรอการเปลี่ยน/ยืนยันโมเดลก่อนงานสาระหลัก ไม่หยุดถามเรื่องโมเดลในค่าเริ่มต้น
